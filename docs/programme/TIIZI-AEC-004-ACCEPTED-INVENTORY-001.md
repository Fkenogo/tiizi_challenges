## 4. Accepted behaviour that PR #171 does not contain

Both PR branches share the same merge-base, `c5776e1d21729c9c09f1c8eb0d67cbc93043bf7e` (PR #147 merge). The comparisons below are therefore attribute-level differences between the two heads, not artefacts of branch age in the merge-base. `#150` is **OPEN** and reported `CONFLICTING` against `main`; `#171` is **OPEN**, `MERGEABLE`, and DRAFT.

### 4.1 New-member Today discovery DOM boundary — `#150` only

`src/v2/today/V2TodayScreen.discovery.dom.test.tsx` (94 lines) exists **only** at the `#150` head. It is absent from the `#171` head and from `origin/main`. It asserts two accepted boundaries:

1. **New zero-active member** — the screen renders "0 active Challenges", the "Discover what fits you" heading, the "Groups to explore" heading with a fallback Group card ("Public walkers"), the "Challenges to explore" heading with a fallback Challenge card ("Morning movement"), **no** "Suggested because" text, and — by `compareDocumentPosition` — the discovery heading **precedes** the "Start with a Group" zero-state panel in DOM order, i.e. recommendations are inside the initial Today viewport rather than below the large empty-state card.
2. **Existing member with an active Challenge** — "1 active Challenge" and "My active Challenge" are rendered, and the "Discover what fits you" heading is **absent**.

**Risk if `#171` is taken alone:** the new-member recommendation *placement* boundary and the member-vs-newcomer *visibility* boundary lose their DOM regression coverage. `#171` carries the equivalent Today coverage in `V2TodayDiscoveryRecommendations.dom.test.tsx` (323 lines) and `todayDiscovery.test.ts` (60 lines), and the `#150` file is byte-identical to neither.

### 4.2 Challenge discovery lifecycle labelling — `#150` only

`src/v2/challenges/challengeDiscovery.test.ts` (23 lines) exists **only** at the `#150` head. It asserts the `lifecycleBucket` classification: `establishment` → `upcoming`; `active` before its governed start date → `upcoming`; a started `active` Challenge → `active`; `ended` → `completed`; a `finalized` `establishment` Challenge → `completed`. This is the regression cover for the `#150` PR-body claim that closed, ended, finalized and window-expired Challenges are filtered by the `endStateFor` classifier before preference selection.

**Risk if `#171` is taken alone:** the lifecycle-label boundary has no dedicated unit test in the candidate branch, although the underlying `src/v2/challenges/challengeDiscovery.ts` module is present in both.

### 4.3 Group pagination stall detection — `#150` carries the weaker guard

`src/v2/today/V2TodayDiscoveryRecommendations.tsx` differs between the heads:

- **`#171`**: `groupPaginationStalled = insufficientGroups && groups.hasNextPage && !groups.isLoading && !groups.isError && !groups.isFetchingNextPage && !groups.isFetchNextPageError && (!nextGroupCursor || repeatedGroupCursor);`
- **`#150`**: `groupPaginationStalled = insufficientGroups && repeatedGroupCursor;`

The Challenge-side guard is identical in both heads (`challengePaginationStalled` with the full flag set and the `!nextChallengeCursor` case). `#150` therefore **does not** detect a stalled Group pagination when the server reports no further cursor, and does not exclude in-flight/error states from the stall condition. **This is an accepted-behaviour difference in the weaker direction for `#171`**: `#171` is the stricter implementation, and the `#150` behaviour must not be transplanted over it. This is the reverse risk to §4.1–§4.2 and is recorded so that the reconciliation does not introduce a regression by importing `#150` wholesale.

### 4.4 "Create a Challenge" / "Launch Challenge" destination

- `#171` (and `origin/main`) route to `/v2/challenges/start` (`V2ChallengeStartScreen`).
- `#150` routes to `/v2/challenges/new` (`V2ChallengeCreationWizard`) from `V2TodayScreen.tsx` and from `V2GroupHomeScreen.tsx`.

`#150`'s branch does not contain the `challenges/start`, `challenges/templates`, `challenges/templates/:templateId`, `challenges/:challengeId/history` or `profile/challenges` routes at all (it is based on `c5776e1`, which predates their merge into `main`), so `#150` links to `/v2/challenges/new` for that reason. The **destination is not adjudicated here**. `origin/main` and `#171` both resolve `/v2/challenges/start` to an existing screen, so `#171`'s target is the reconcilable one; `#150`'s target is a divergence that the reconciliation must settle explicitly rather than by accident.

### 4.5 Route and template preservation — merge hazard in `#150`

`origin/main:src/v2/routes.tsx` serves `challenges/start`, `challenges/templates`, `challenges/templates/:templateId`, `challenges/:challengeId/history` and `profile/challenges`. The `#150` head's `src/v2/routes.tsx` **removes** all five relative to `#171`/`main` (it deletes the corresponding template, history and profile-history screens and their imports). Merging or transplanting `#150` wholesale would **delete merged template, streak-history and profile-history functionality**. Only bounded file-level transplants from `#150` are admissible.

## 9. Update discipline

1. **Every AEC-004 pull request updates this extract.** On each AEC-004 PR, PC-1 records, in the same PR or an immediately following bounded PR: the PR number and exact head SHA; the fetched `origin/main` SHA and fetch time; the register IDs affected; which accepted sources were transplanted and which were deliberately omitted; the resulting MERGED / TESTED / PREVIEW VERIFIED status per affected register ID; and any newly discovered divergence.
2. **One row per register ID, maintained, never re-created.** The canonical register remains the authoritative ledger; this extract is the AEC-004 working view of it. Rows are updated in place with new dates and SHAs. A row is never deleted to signal completion — completion is recorded as a dated status change with evidence.
3. **No silent closure.** A register entry closes only when its evidence and the current `main` are reconciled and the closure is recorded. Until then it reads `ACCEPTED / INTEGRATION OPEN`. An entry is never marked `DEPLOYED` without runtime/deployment evidence.
4. **Founder supersession requires a new dated record with the exact accepted source.** Removed or changed accepted behaviour must be recorded as an explicit Founder supersession naming the superseded decision, its date, the new decision, its date, the new exact accepted source SHA, branch and paths, and the register IDs affected. The prior decision and its source pointer are retained. In the absence of such a record, the existing accepted behaviour stands and this extract may not be edited to remove it.
5. **No redesign by default.** If accepted behaviour is missing from a candidate, it is recovered or reconciled, not redesigned. Any proposed redesign requires its own Founder record.
6. **UNKNOWN is preserved.** Where evidence is missing, the field reads `UNKNOWN`. It is never replaced with an inference, a PR description, or a plausible guess.
7. **Preserved sources are not pruned.** Accepted source branches and worktrees are retained until preservation is proved on merged `main` (AEC-001 §5.9).
