# Founder Authorization Validation Checklist

**Document type:** Reusable programme-governance validation checklist

**Programme:** Tiizi Version 2

**Checklist status:** Founder-approved integrated programme-governance checklist; validation does not itself authorize work

## 1. Use

Complete this checklist for one proposed work package after planning and before work begins. Record evidence for every applicable item.

The checklist validates readiness and decision integrity. It cannot supply a missing Founder decision, waive a dependency or update the Master Programme.

## 2. Package Identity

- [ ] Exact work-package identifier recorded.
- [ ] Exact work-package title recorded.
- [ ] Programme stage recorded.
- [ ] Programme phase recorded.
- [ ] One bounded subject recorded, or decomposition separately approved.
- [ ] Planning package linked.

**Evidence:** `[relative links and section references]`

## 3. Planning Readiness

- [ ] Purpose is explicit.
- [ ] Included scope is explicit.
- [ ] Exclusions are explicit.
- [ ] Deliverables are explicit.
- [ ] Inputs and dependencies are explicit.
- [ ] Founder questions and blockers are explicit.
- [ ] Entry gates are explicit.
- [ ] Completion evidence is explicit.
- [ ] Planning non-effects are explicit.
- [ ] Planning validation has passed.

**Evidence:** `[relative links and section references]`

## 4. Dependency Verification

- [ ] Every material dependency is listed.
- [ ] Every dependency type is identified.
- [ ] Every required dependency condition is stated.
- [ ] Every dependency status is evidenced.
- [ ] Every blocking effect is stated.
- [ ] No blocking dependency remains unsatisfied.
- [ ] Deferred matters are preserved without silent resolution.
- [ ] No dependency is reinterpreted or amended by the authorization package.

**Evidence:** `[relative links and section references]`

## 5. Programme-State Verification

- [ ] Current Master Programme version recorded.
- [ ] Active stage and phase verified.
- [ ] Proposed package is permitted by the programme sequence.
- [ ] Preceding required completion evidence exists.
- [ ] Stage dependencies remain satisfied.
- [ ] Stage completion gate remains unchanged.
- [ ] No conflicting package occupies the same boundary.
- [ ] Programme synchronization is identified as a required post-decision entry gate.

**Evidence:** `[Master Programme link, version and section references]`

## 6. Founder Decision Integrity

- [ ] Founder decision is explicit.
- [ ] Founder attribution is explicit.
- [ ] Decision outcome uses an allowed outcome.
- [ ] Authorization date is recorded.
- [ ] Authorized identifier and title match the validated plan.
- [ ] Authorized scope matches the validated plan or records an attributable amendment.
- [ ] Dependencies, entry gates and exclusions are preserved.
- [ ] Conditions are recorded exactly.
- [ ] Founder notes are recorded exactly.
- [ ] Authorization statement approves no future output.

**Evidence:** `[Founder authorization record link and section references]`

## 7. Authorization Boundary

- [ ] Authorization applies to one identified package only.
- [ ] Authorization does not transfer by sequence or similarity.
- [ ] Authorization does not extend to a successor package.
- [ ] Material boundary changes require new or amended authorization.
- [ ] Authorization does not complete the package, phase or stage.
- [ ] Authorization does not satisfy an incomplete dependency.
- [ ] Authorization does not resolve deferred decisions by implication.

**Evidence:** `[authorization record section references]`

## 8. Constitutional and Accountability Non-Effects

- [ ] No constitutional doctrine is created.
- [ ] No constitutional proposition is introduced.
- [ ] No Platform Authority is created, extended or redistributed.
- [ ] No accountability relationship is allocated.
- [ ] No role or permission is created.
- [ ] Existing governance remains unchanged.

**Evidence:** `[scope validation and authorization record references]`

## 9. Implementation and Repository Non-Effects

- [ ] No implementation is authorized unless implementation is the expressly bounded package subject.
- [ ] No deployment, migration, release or publication is authorized by implication.
- [ ] Repository files, branches, commits or paths are not treated as authorization.
- [ ] Repository administration is not treated as programme authority.
- [ ] Technical mechanisms are not treated as decision evidence unless the authorization record identifies them as supporting evidence.

**Evidence:** `[authorization boundary references]`

## 10. Programme Synchronization

- [ ] Founder authorization record is complete.
- [ ] All authorization conditions are satisfied.
- [ ] Master Programme identifies the package as the authorized next action.
- [ ] Master Programme preserves existing stage dependencies and completion gates.
- [ ] Programme change-log entry is attributable.
- [ ] No unrelated package is advanced.
- [ ] No broader authorization is implied.

**Evidence:** `[Master Programme link, version and change-log entry]`

## 11. Mechanical Validation

- [ ] Required documents exist.
- [ ] Relative links resolve.
- [ ] Markdown structure passes.
- [ ] Trailing whitespace check passes.
- [ ] EOF check passes.
- [ ] `git diff --check` passes where repository work is involved.
- [ ] Unrelated worktree changes remain untouched.

**Evidence:** `[validation output or report]`
