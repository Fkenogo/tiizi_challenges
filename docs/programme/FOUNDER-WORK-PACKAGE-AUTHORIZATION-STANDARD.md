# Founder Work Package Authorization Standard

**Document type:** Programme-governance standard

**Programme:** Tiizi Version 2

**Applicability:** Every bounded governance, product-translation, engineering-alignment and implementation work package

**Status:** Founder-approved programme governance; integrated through Master Programme Version 1.5

**Date:** 2026-07-23

## 1. Purpose

This standard defines the programme authorization that must occur before a new bounded Tiizi Version 2 work package begins. It provides one reusable control across every programme stage without changing the purpose, dependency, completion gate or constitutional status of any stage.

Work-package authorization confirms that the Founder has permitted an identified, bounded package to begin after its planning and dependencies have been reviewed. Authorization is not approval of the package’s future outputs.

## 2. Programme-Governance Boundary

This standard governs programme sequence and permission to begin work. It is not constitutional governance, a constitutional amendment procedure, product governance, technical architecture or implementation guidance.

It:

- authorizes no specific work package;
- creates no constitutional proposition or doctrine;
- creates no Platform Authority;
- allocates no accountability relationship, role or permission;
- changes no Master Programme stage, dependency or completion gate; and
- does not modify or supersede any existing governance instrument.

## 3. Applicability

The standard applies whenever a new bounded work package is proposed within the Tiizi Version 2 Master Programme, including work under Stages D, E0, EK, E1, F, G and H.

The same authorization discipline applies whether the proposed work is analytical, constitutional, governance-related, documentary, translational, technical or implementation-focused. The content rules governing those subjects remain supplied by their own approved dependencies.

Routine activity already contained within an expressly authorized work package does not require a new work-package authorization unless its scope, subject, dependencies, deliverables, exclusions or completion gate materially changes.

## 4. Authorization Purpose

Founder work-package authorization exists to confirm that:

1. the proposed package has one identifiable programme purpose;
2. its place in the approved programme sequence is known;
3. prerequisite work and dependencies have been verified;
4. its planning boundary is complete enough to govern execution;
5. the work to be performed and the work expressly excluded are distinguishable;
6. its evidence and completion gates are reviewable;
7. no unresolved blocker is being bypassed; and
8. the Founder has expressly authorized that bounded package to begin.

Authorization must be explicit and attributable. Sequence, expectation, prior discussion, planning completion, repository preparation or another package’s completion does not substitute for Founder authorization.

## 5. Authorization Prerequisites

Before authorization may be requested, the proposed package must have:

- an exact proposed identifier and title;
- a stated programme stage and phase;
- a single bounded purpose or an approved decomposition into bounded packages;
- a scope statement;
- explicit exclusions;
- expected deliverables;
- identified authoritative and supporting dependencies;
- dependency status for every dependency;
- known blockers, Founder questions and deferred matters;
- entry gates;
- completion and validation evidence requirements;
- a statement of programme effects and non-effects;
- confirmation that preceding required work is complete or otherwise permits the proposed package; and
- a planning validation showing that the package does not exceed its governing programme boundary.

Missing prerequisites remain visible. They must not be silently inferred, waived or marked complete.

## 6. Dependency Verification

Dependency verification must identify for every material dependency:

| Required field | Programme purpose |
|---|---|
| Dependency | Identifies the governing or preceding source. |
| Dependency type | Distinguishes programme, governance, decision, evidence, technical or implementation dependency. |
| Required condition | States what the proposed package needs from the dependency. |
| Current status | Records whether the dependency is satisfied, incomplete, deferred, blocked or not applicable. |
| Evidence | Links the attributable source supporting the recorded status. |
| Blocking effect | States whether an unsatisfied condition prevents authorization or only influences later work. |

An incomplete blocking dependency prevents authorization. A deferred or unresolved matter may be carried into the work package only when the plan expressly preserves it and the package is not required to resolve it.

Dependency verification does not reinterpret, amend or approve the dependency.

## 7. Required Programme State

Before work begins:

1. the Master Programme must be consulted as the current programme source of truth;
2. the proposed package must be permitted by the recorded stage and dependency sequence;
3. the active stage and phase must remain accurately stated;
4. the preceding required package must have the necessary completion evidence;
5. the Founder authorization must be recorded;
6. the Master Programme must be synchronized to identify the authorized package as the next permitted action; and
7. no conflicting package may already occupy the same programme boundary.

Founder authorization and Master Programme synchronization are separate controls. A planning document cannot update programme state, and a programme entry cannot replace attributable Founder authorization.

## 8. Required Planning State

Planning must be complete enough to provide:

- a stable work-package identity;
- one bounded subject or approved package decomposition;
- scope and exclusions;
- inputs and dependencies;
- unresolved questions and blockers;
- deliverables;
- execution boundaries;
- validation objectives;
- completion gates; and
- a decision-ready authorization request.

Planning may recommend authorization. It must not claim authorization, begin substantive work or present planned outputs as completed.

## 9. Founder Authorization Statement

An attributable Founder authorization record must contain:

- work-package identifier;
- work-package title;
- programme stage and phase;
- reference to the approved planning package;
- decision outcome;
- authorization date;
- authorized scope;
- preserved exclusions;
- prerequisite and dependency finding;
- entry gates that remain applicable;
- express non-effects; and
- Founder attribution.

The authorization statement should use this programme wording:

> The Founder authorizes `[work-package identifier] — [work-package title]` to begin within the approved planning scope, dependencies, entry gates and exclusions. This authorization permits only the identified work package and approves none of its future outputs.

This wording records programme authorization only. It does not identify or exercise a Platform Authority.

## 10. Authorization Boundary

Authorization is bounded to the identifier, title, subject, scope, deliverables, dependencies, entry gates and exclusions expressly recorded.

It does not transfer by:

- sequence;
- similarity;
- shared stage or phase;
- shared personnel;
- shared files;
- dependency;
- naming convention;
- repository location; or
- completion of the authorized package.

A material change to the authorized boundary requires an attributable Founder amendment or a new authorization before the changed work begins.

## 11. Non-Effects

Work-package authorization does not:

- approve, adopt or make effective any future deliverable;
- declare the work package complete;
- complete a phase or stage;
- authorize a successor package;
- satisfy a dependency that remains incomplete;
- resolve a Founder decision, governance question or technical decision reserved to the package;
- create constitutional meaning;
- create or extend a Platform Authority;
- allocate accountability, roles or permissions;
- approve implementation, deployment, migration, release or publication unless that action is expressly the bounded subject;
- amend the Master Programme by itself; or
- amend, supersede or reinterpret approved governance.

## 12. Prohibited Interpretations

The following interpretations are prohibited:

- “Planned” means authorized.
- “Next in sequence” means authorized.
- “Ready” means authorized.
- “Founder reviewed” means authorized unless an attributable authorization decision is recorded.
- “Repository files exist” means work may begin.
- “A related package was authorized” extends authorization to this package.
- “No objection was recorded” constitutes authorization.
- “An agent or contributor began work” proves authorization.
- “Authorization to draft” approves the draft.
- “Authorization to implement” permits changes outside the recorded boundary.
- “Completion” authorizes the next package.

## 13. Required Authorization Evidence

The minimum programme evidence set consists of:

1. a bounded planning package;
2. dependency verification;
3. a Founder authorization decision or explicit refusal, amendment or deferral;
4. a completed Founder authorization record;
5. a passed [Founder Authorization Validation Checklist](FOUNDER-WORK-PACKAGE-AUTHORIZATION-VALIDATION-CHECKLIST.md); and
6. Master Programme synchronization before work begins.

The [Founder Work Package Authorization Template](FOUNDER-WORK-PACKAGE-AUTHORIZATION-TEMPLATE.md) supplies the reusable record format. The [Work Package Authorization Lifecycle](WORK-PACKAGE-AUTHORIZATION-LIFECYCLE.md) defines the programme sequence.

## 14. Authorization Outcome

An authorization review must end in exactly one recorded outcome:

- **Authorized** — the bounded package may begin after all remaining entry gates, including programme synchronization, pass;
- **Authorized with explicit conditions** — the package may begin only after every recorded condition is satisfied;
- **Amended** — the Founder changes the proposed boundary and requires the amended plan to be revalidated;
- **Deferred** — no work may begin until a later attributable decision;
- **Rejected** — no work may begin under the proposed package; or
- **Blocked** — authorization cannot be decided because a stated prerequisite or dependency is unsatisfied.

Only **Authorized**, or **Authorized with explicit conditions** after those conditions are evidenced as satisfied, may progress to Master Programme synchronization and work-package commencement.

## 15. Standard Status

This standard is a reusable programme-governance control integrated through Founder-approved Master Programme Version 1.5. It governs programme authorization within its stated boundary and does not authorize any work package or change the Master Programme by itself.
