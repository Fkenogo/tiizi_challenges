# EOG-01 — Platform Accountability Framework Founder Decision Pack

## 1. Purpose

This pack prepares founder decisions required to approve the universal accountability relationship framework.

It does not assign a relationship to any Governed subject, approve the prior EOG-01 allocation-pattern recommendation, amend the Entity Ownership Register or resolve EOG-02 through EOG-06.

The pack covers:

- Decision Agenda;
- Decision Options;
- Decision Sequence;
- Decision Criteria.

Every recommendation is labelled **Recommended — pending founder approval** and has no governance effect until explicit approval is recorded.

## 2. Constitutional Guardrails

Every framework decision must preserve:

1. the conceptual precedence of Document 00;
2. the non-constitutional guidance role of Document 00A;
3. the eleven approved Platform Authority types;
4. one declared Authority per authoritative truth;
5. one Accountable steward per Governed subject when later allocated;
6. Authority, stewardship and custody as distinct relationships;
7. administration, operation, presentation, origin and use as distinct relationships;
8. explicit, attributable and limited delegation;
9. least privilege, privacy and historical attribution;
10. no allocation in this phase.

## 3. Decision Criteria

Each option is assessed against these criteria.

| Criterion | Question |
|---|---|
| Constitutional clarity | Does the option preserve one meaning for each relationship? |
| Separation of concerns | Does it prevent Authority, stewardship, custody, operation and presentation from collapsing? |
| Accountability clarity | Can a later register state who is answerable for what without ambiguity? |
| Attribution | Can origin, decision, delegation and presentation remain distinguishable? |
| Least privilege | Does the relationship grant only the minimum scope implied by its purpose? |
| Privacy compatibility | Can the relationship operate without implying unrestricted access or control? |
| Domain neutrality | Can the relationship remain stable across Fitness, Wellness and future governed domains? |
| Implementation neutrality | Does it remain valid regardless of organization or technology? |
| Scalability | Can future subjects use the vocabulary without inventing local meanings? |
| Simplicity | Is the vocabulary no larger than necessary for constitutional clarity? |
| Auditability | Can a consequential action identify the relationship through which it occurred? |
| Reversibility | Could the decision later change without reinterpreting historical accountability? |

### Decision Assessment Scale

- **Difficulty:** Low, Medium or High.
- **Risk:** Low, Medium or High.
- **Reversibility:** Easy, Moderate or Constitutionally difficult.
- **Long-term impact:** Low, Medium or High.

## 5. Decision Options

### EOG-01-FW-01 — Canonical Relationship Set

**Decision question:** Which relationships are necessary for universal accountability definition?

#### Option A — Minimal Accountability Set

Define only Authority, Accountable steward, Custodian and Operator.

**Advantages:** Short vocabulary; easy initial review.

**Disadvantages:** Leaves origin, contribution, participation, administration, delegation, presentation and downstream use to local interpretation; later registers still need those distinctions.

**Constitutional effect:** Retains existing core but does not fully operationalize the Entity Ownership Foundation's normalized vocabulary.

#### Option B — Complete Bounded Relationship Set

Define Authority, Authority to establish truth, Accountable steward, Custodian, Operator, Administrator, Contributor, Participant, Governed subject, Information subject, Attributable originator, Delegate, Delegating party, Presenter and Downstream user.

**Advantages:** Covers every relationship already used or demonstrably required; minimizes local invention; supports traceable later allocation.

**Disadvantages:** Larger vocabulary; requires disciplined use and founder review of three new terms.

**Constitutional effect:** Refines semantics without creating a new Authority or allocation.

#### Option C — Domain-Defined Relationship Sets

Let each domain define its own accountability vocabulary.

**Advantages:** Maximum local flexibility.

**Disadvantages:** Creates semantic drift, overlap and competing meanings; weakens cross-domain registers.

**Constitutional effect:** Conflicts with canonical terminology and Platform Before Feature.

**Recommended — pending founder approval:** Option B.

**Reason:** It is the smallest set that accounts for truth, stewardship, preservation, operation, contextual input, delegation, communication and use without conflation.

**Difficulty:** Medium. **Risk:** High. **Reversibility:** Moderate. **Long-term impact:** High.

**Founder decision:**

- [ ] Request another bounded set

### EOG-01-FW-02 — Formal Stewardship Terminology

**Decision question:** How should formal governance use “Steward”?

#### Option A — Accountable Steward Is Formal

Use “Accountable steward” in formal governance. Permit “Steward” only as unambiguous explanatory shorthand.

**Advantages:** Preserves existing canonical wording and makes answerability explicit.

**Disadvantages:** Longer term in ordinary prose.

#### Option B — Steward Is Formal and Equivalent

Replace “Accountable steward” with “Steward” everywhere.

**Advantages:** Simpler language.

**Disadvantages:** “Steward” can describe contribution, care or administration without ultimate accountability; creates ambiguity during allocation.

#### Option C — Multiple Stewardship Tiers

Create principal, co-, domain and operational stewards.

**Advantages:** Reflects collaborative organizations.

**Disadvantages:** Risks multiple accountable stewards and collapses custody or operation into stewardship.

**Constitutional effect:** Option C conflicts with the existing one-Accountable-steward rule unless the foundation is amended.

**Recommended — pending founder approval:** Option A.

**Reason:** Formal language should identify answerability precisely while allowing readable shorthand outside allocations.

**Difficulty:** Low. **Risk:** Medium. **Reversibility:** Moderate. **Long-term impact:** High.

### EOG-01-FW-03 — Subject Terminology

**Decision question:** How should formal governance use “Subject”?

#### Option A — One Generic Subject Term

Use Subject for both what governance governs and whom information concerns.

**Advantages:** Short and familiar.

**Disadvantages:** Conflates governance object, information concern and human subject; creates ownership and privacy ambiguity.

#### Option B — Preserve Two Canonical Subject Terms

Require “Governed subject” and “Information subject” in formal governance. Allow unqualified Subject only in unambiguous explanatory prose.

**Advantages:** Preserves existing constitutional distinction and supports accurate registers.

**Disadvantages:** Requires careful terminology.

#### Option C — Add More Universal Subject Types Now

Create Data subject, Decision subject and Beneficiary as additional constitutional relationships.

**Advantages:** Could support future specialized governance.

**Disadvantages:** Premature; some are legal, policy or domain concepts rather than universal accountability relationships.

**Recommended — pending founder approval:** Option B.

**Reason:** The existing two-term distinction is sufficient and prevents the most consequential ambiguity without speculative additions.

**Difficulty:** Low. **Risk:** Medium. **Reversibility:** Moderate. **Long-term impact:** High.

### EOG-01-FW-04 — Delegation and Assignment Model

**Decision question:** How should Tiizi distinguish delegated Authority, assigned responsibility and stewardship reassignment?

#### Option A — One General Delegation Concept

Treat every transfer of work, Authority, custody or accountability as delegation.

**Advantages:** Simple vocabulary.

**Disadvantages:** Obscures what transferred; may silently transfer Authority or stewardship; weakens attribution.

#### Option B — Differentiated Model

Use:

- delegation for explicit transfer of limited Authority;
- assignment for responsibility, custody, administration, operation or presentation duties;
- governed reassignment for change of Accountable steward.

**Advantages:** Preserves source, scope and one-steward rule; supports reviewability and least privilege.

**Disadvantages:** Requires precise declarations and later process standards.

#### Option C — No Delegation

Require the original Authority or accountable party to perform every action.

**Advantages:** Simple attribution.

**Disadvantages:** Unscalable and inconsistent with the approved Authority Model's delegation rules.

**Recommended — pending founder approval:** Option B.

**Reason:** Different constitutional relationships cannot transfer through one undifferentiated mechanism.

**Difficulty:** High. **Risk:** High. **Reversibility:** Constitutionally difficult. **Long-term impact:** High.

### EOG-01-FW-05 — Relationship Composition

**Decision question:** May the same actor hold several accountability relationships?

#### Option A — Exclusive Relationship Model

One actor may hold only one relationship concerning a Governed subject.

**Advantages:** Strong separation in appearance.

**Disadvantages:** Impractical; confuses separation of relationships with separation of actors; creates unnecessary organizational assumptions.

#### Option B — Explicit Relationship Stacking

One actor may later hold several relationships where governance permits, but each relationship, purpose and scope must be declared separately.

**Advantages:** Implementation-neutral, practical and auditable; prevents implied expansion.

**Disadvantages:** Requires conflict-of-interest governance and disciplined attribution later.

#### Option C — Role-Bundle Inference

A role title automatically carries its customary Authority, stewardship, custody and operation.

**Advantages:** Concise allocation.

**Disadvantages:** Conflicts with declared Authority, least privilege and the rule that role names do not create Authority.

**Recommended — pending founder approval:** Option B.

**Reason:** Constitutional separation concerns meanings and scopes, not mandatory organizational fragmentation.

**Difficulty:** Medium. **Risk:** High. **Reversibility:** Moderate. **Long-term impact:** High.

### EOG-01-FW-06 — Contributor and Participant Treatment

**Decision question:** Should contextual input relationships appear in the accountability framework?

#### Option A — Exclude Both

Keep Contributor and Participant only in domain standards.

**Advantages:** Smaller universal vocabulary.

**Disadvantages:** Later registers may confuse contribution or participation with origin, approval or Authority.

#### Option B — Include as Non-Authority Contextual Relationships

Define Contributor as attributable input and Participant as governed participation context. State explicitly that neither relationship grants approval, stewardship, custody or general Authority.

**Advantages:** Makes origin and input traceable; prevents status from becoming Authority; supports cross-domain extension without activating future scope.

**Disadvantages:** Participant remains currently Challenge-specific and must retain that launch boundary.

#### Option C — Give Contributor or Participant Default Approval Rights

Treat contribution or participation as authority over the resulting information or Undertaking.

**Advantages:** Appears participatory.

**Disadvantages:** Collapses origin with acceptance, approval and stewardship; conflicts with the Authority chain.

**Recommended — pending founder approval:** Option B.

**Reason:** Contextual relationships belong in the framework precisely so that their non-authoritative boundary is universal.

**Difficulty:** Medium. **Risk:** High. **Reversibility:** Moderate. **Long-term impact:** Medium.

### EOG-01-FW-07 — Custody and Possession

**Decision question:** How should custody relate to storage, protection and multiple custodial purposes?

#### Option A — Exactly One Custodian Per Governed Subject

Assign one constitutional Custodian for all information and purposes.

**Advantages:** Simple accountability label.

**Disadvantages:** Conflates different information, purposes and handling contexts; may be impractical across domains.

#### Option B — Purpose-Limited Custody

Allow one or more expressly scoped custodial relationships where later governance requires them. Storage or possession alone has no constitutional effect.

**Advantages:** Preserves one Accountable steward while supporting distinct preservation purposes; implementation-neutral.

**Disadvantages:** Requires a custody map and clear boundaries among Custodians.

#### Option C — Possession Implies Custody

Treat the party holding or storing information as its Custodian.

**Advantages:** Easy to infer.

**Disadvantages:** Confuses technical possession with governed responsibility; creates accidental custody and Authority expectations.

**Recommended — pending founder approval:** Option B.

**Reason:** Custody is a declared purpose relationship, not a side effect of where information happens to be held.

**Difficulty:** Medium. **Risk:** High. **Reversibility:** Moderate. **Long-term impact:** High.

### EOG-01-FW-08 — Framework Adoption Effect

**Decision question:** What effect should founder approval of the framework have?

#### Option A — Mandatory Semantics, No Allocations

Make the approved definitions and distinctions mandatory for later governance and allocation work. Require controlled alignment of terminology and validation, but leave every allocation pending.

**Advantages:** Prevents semantic drift; gives later phases a stable vocabulary; preserves decision sequence.

**Disadvantages:** Requires later documentation alignment and disciplined exception handling.

#### Option B — Advisory Guidance Only

Allow later standards to use or redefine the relationships.

**Advantages:** Maximum local flexibility.

**Disadvantages:** Recreates the ambiguity the framework exists to solve.

#### Option C — Framework Approval Plus Allocation Approval

Treat approval as also selecting the prior hybrid allocation pattern or assigning register relationships.

**Advantages:** Faster register completion.

**Disadvantages:** Violates this phase's no-allocation boundary and would conflate semantic approval with substantive allocation.

**Recommended — pending founder approval:** Option A.

**Reason:** The framework should govern meaning before later decisions govern allocation.

**Difficulty:** Low. **Risk:** High. **Reversibility:** Constitutionally difficult after allocations rely upon it. **Long-term impact:** High.

## 7. Recommended Decision Sequence

The eight decisions can be reviewed in one focused founder session because all concern universal semantics rather than entity allocation.

### Stage 1 — Define the Vocabulary

1. EOG-01-FW-01 — Canonical relationship set
2. EOG-01-FW-02 — Formal stewardship terminology
3. EOG-01-FW-03 — Subject terminology

These establish the words later choices use.

### Stage 2 — Define Transfer and Composition

4. EOG-01-FW-04 — Delegation and assignment
5. EOG-01-FW-05 — Relationship composition

These establish how relationships coexist or move without merging.

### Stage 3 — Define Context and Custody

6. EOG-01-FW-06 — Contributor and Participant
7. EOG-01-FW-07 — Custody and possession

These close the primary origin, context and preservation ambiguities.

### Stage 4 — Approve Effect

8. EOG-01-FW-08 — Framework adoption effect

This determines whether the approved semantics become mandatory for later work.

### Session Estimate

One 75–90 minute founder session is the smallest practical review structure. If split, end Session A after EOG-01-FW-04 and begin Session B with relationship composition.

## 8. Approval Consequences

Approval of the recommended framework options would:

- establish universal relationship semantics;
- unblock terminology alignment and a revised EOG-01 allocation-pattern session;
- give the Entity Ownership Register a stable definition basis;
- support later lifecycle, role, permission, privacy, security and implementation standards;
- leave every entity allocation pending;
- leave EOG-02 through EOG-06 pending;
- leave the prior hybrid allocation recommendation pending.

## 9. Deferral Consequences

If framework approval is deferred:

- the draft remains analysis only;
- existing baseline terminology remains authoritative;
- Contributor, Delegate and Delegating party remain non-canonical;
- “Steward” and unqualified “Subject” remain potentially ambiguous;
- allocation work should not proceed using the draft as if approved;
- EOG-02 through EOG-06 may continue as analysis but should not assume the draft vocabulary is constitutional.
