# TIIZI V2 INITIAL CANONICAL ACTIVITY BASELINE --- FOUNDER WORKING BASELINE

**Document type:** Founder Working Baseline\
**Status:** Substantively Settled for Stage EK Canonical Activity
Development\
**Date:** 2026-09-02\
**Scope:** Initial V2 canonical Activity baseline for the unified Tiizi
Knowledge Base\
**Authority note:** This is a working baseline supporting Stage EK. It
is not a separate constitutional instrument and does not authorize
implementation.

------------------------------------------------------------------------

## 1. Purpose

This baseline records the initial V2 set of canonical Activities
proposed to populate Tiizi's unified Activity Knowledge library.

It is the result of a fresh V2 review rather than a preservation
exercise over the V1 catalogues. Historical Fitness and Wellness
catalogues were treated as evidence and source material, not as target
catalogue sizes or binding taxonomies.

The baseline establishes:

-   the unified Activity-library structure;
-   the initial Fitness and Wellness categories;
-   the initial canonical Activity candidates;
-   the working Activity Knowledge record model;
-   measurement compatibility principles;
-   canonical-versus-variant principles;
-   the boundary between Activity Knowledge, Challenge Templates and
    final Challenges;
-   publication dependencies requiring further content or guidance;
-   the principle of continued governed library evolution through Tiizi
    administration.

The initial baseline contains **118 canonical Activity candidates: 84
Fitness and 34 Wellness**.

This is an initial governed baseline, not a claim that the Tiizi
Activity library is complete or permanently closed.

------------------------------------------------------------------------

## 2. Governing Activity Knowledge boundary

The Activity Knowledge Base defines reusable canonical Activity meaning,
compatible measurement, participant guidance and governed relationships.

A canonical Activity should answer:

> **What is this Activity, how is it normally performed, how can it
> legitimately be measured, and what should someone know to perform it
> appropriately?**

It should not prescribe the final structure of every Challenge that may
use it.

The governing relationship is:

``` text
Canonical Activity Knowledge
        ↓
Challenge Template
        ↓
Creator / participant customization
        ↓
Final Challenge
```

The Activity remains canonical and reusable across Challenge types and
configurations.

Challenge Templates are reusable starting points. They do not become the
final Challenge merely because they reference canonical Activities.

The final Challenge determines the actual undertaking, subject to
applicable product and governance constraints.

------------------------------------------------------------------------

## 3. Unified Knowledge Base architecture

``` text
Tiizi Knowledge Base
└── Activity Knowledge
    ├── Fitness
    │   └── Exercise Assets
    └── Wellness
        └── Wellness Activity Assets
```

Fitness and Wellness are domains within one Activity Knowledge system,
not separate knowledge systems.

Exercise Assets and Wellness Activity Assets retain their
domain-specific identities while sharing the common canonical Activity
foundation.

The same governed Activity Knowledge is intended to support downstream
mechanisms including:

-   Challenge Wizard;
-   Challenge Templates;
-   discovery;
-   recommendations;
-   Activity selection and logging;
-   historical interpretation.

One canonical Activity may have multiple legitimate contexts without
being duplicated across domains.

------------------------------------------------------------------------

## 4. Working canonical Activity record model

The working Activity record should support the following structure.

### 4.1 Identity

-   Canonical ID
-   Name
-   Domain
-   Category
-   Classification / Family
-   Authoritative Description

### 4.2 Performance Knowledge

As appropriate to the Activity:

-   execution characteristics;
-   how to perform the Activity;
-   Activity Guidance;
-   common mistakes / don'ts;
-   difficulty and adaptation guidance;
-   equipment or environment considerations;
-   safety or caution guidance.

Not every Activity requires the same depth of guidance.

### 4.3 Measurement Knowledge

-   Compatible Metrics
-   Compatible Units
-   Measurement Guidance where genuinely useful

Compatibility establishes what makes semantic sense for an Activity. It
does not determine the final target or Challenge structure.

### 4.4 Relationships

As appropriate:

-   Variants / Modifications
-   Related Activities
-   Equipment Relationships
-   contextual relationships
-   other governed classifications

### 4.5 Governance

-   Provenance
-   Lifecycle State
-   Publication State
-   Runtime Availability

------------------------------------------------------------------------

## 5. Matters deliberately excluded from canonical Activity identity

The following are not hardcoded into canonical Activity identity merely
because a Challenge may use them:

-   target value;
-   sets;
-   repetitions per set;
-   per-side requirement;
-   frequency;
-   schedule;
-   time window;
-   Challenge duration;
-   Challenge type;
-   streak rules;
-   collective rules;
-   competitive rules;
-   scoring;
-   ranking;
-   participant customization.

These belong downstream in Challenge Template and/or final Challenge
configuration.

For example, Push-Up may be compatible with Repetitions. One Challenge
may require 100 total repetitions with sets unspecified; another may
structure the same target as 5 sets of 20. The canonical Push-Up
Activity does not need to prescribe either structure.

------------------------------------------------------------------------

## 6. Measurement model relationship

The Activity baseline uses the Founder Working Baseline measurement
architecture:

``` text
Activity
    ↓
Compatible Metric
    ↓
Compatible Unit
    ↓
Challenge-selected Target / condition
```

The six working canonical Metrics are:

1.  Completion
2.  Repetitions
3.  Duration
4.  Distance
5.  Weight
6.  Quantity

No seventh core Metric was required by the 118-Activity baseline.

### 6.1 Compatibility is not prescription

A compatible Metric indicates that the measurement is semantically
meaningful for the Activity.

It does not mean:

-   every Challenge must use that Metric;
-   every theoretically possible Metric must be provisioned;
-   a Metric determines canonical Activity identity;
-   the Activity Knowledge fixes the target value.

### 6.2 Completion

Completion is used where completion of a configured occurrence or
practice is itself a meaningful measurement form.

It should not be attached to every Activity merely because a Challenge
can eventually be completed.

### 6.3 Quantity

Quantity always requires an explicit semantic Unit.

Initial demonstrated Quantity Units include:

-   steps;
-   millilitres;
-   litres;
-   servings;
-   pages;
-   acts;
-   flights.

------------------------------------------------------------------------

## 7. Canonical Activity versus Variant

A canonical Activity is a distinct undertaking Tiizi can independently
select, define, measure and interpret.

A Variant is a governed modification that changes how an Activity is
performed without necessarily creating a materially different
undertaking.

An independent canonical identity is justified where authoritative
meaning, normal measurement contract, material execution mechanics,
participant-facing undertaking, or governance requirements require
independent representation.

Differences limited primarily to equipment, assistance, resistance,
stance, grip, difficulty or similar execution parameters should
ordinarily remain Variants unless those differences materially alter
canonical meaning.

Examples:

-   Push-Up and Push-Up Hold remain separate canonical Activities.
-   Squat and Squat Hold remain separate.
-   Deadlift and Romanian Deadlift remain separate.
-   Pull-Up and Chin-Up remain separate.
-   weighted Push-Up does not automatically become a separate Activity.
-   barbell, dumbbell and machine Bench Press do not automatically
    become separate Activities.
-   outdoor and stationary Cycling do not automatically become separate
    Activities.

A Variant may later be promoted to canonical status where product
evidence and Knowledge governance justify it.

------------------------------------------------------------------------

## 8. Cross-domain identity principle

Context or purpose does not automatically create a second canonical
Activity.

Examples:

-   Walking remains one canonical Activity under Fitness → Cardio &
    Conditioning even where it is relevant to Wellness contexts.
-   Dance remains one canonical Activity under Fitness → Sports &
    Recreation even where it also relates to creativity or social
    wellbeing.
-   Breathing Practice remains a Wellness Activity even where it is
    useful in physical-training contexts.

Tiizi should not create duplicate identities such as "Fitness Walking"
and "Wellness Walking" merely because the same Activity is used in
different contexts.

## 27. Guidance principle

Activity Guidance exists to help participants understand and
appropriately use an Activity without making the Activity unnecessarily
rigid.

Depending on the Activity, guidance may include:

-   what the Activity is;
-   how it is normally performed;
-   useful form or execution guidance;
-   do's and don'ts;
-   common mistakes;
-   difficulty or adaptation guidance;
-   equipment guidance;
-   environment considerations;
-   safety/caution guidance;
-   measurement guidance where ambiguity genuinely matters.

Guidance should be proportionate to the Activity.

Operational content management may distinguish guidance needs such as
Basic, Enhanced, Safety-Sensitive or Authority-Dependent, but those
working labels do not need to become constitutional governance
classifications.

Advice about sets, difficulty, progression or common approaches may be
included as guidance without turning that advice into a universal
Challenge requirement.

## 28. Publication dependencies

Canonical inclusion and Runtime publication readiness are distinct.

The following initial Activities have identified content dependencies
requiring resolution before relevant Runtime publication:

### 28.1 Fruit Intake

Where `servings` is exposed as a Quantity Unit, Tiizi requires
sufficiently authoritative participant guidance defining the serving
interpretation.

### 28.2 Vegetable Intake

The same serving-definition requirement applies.

### 28.3 Avoid Added Sugar

Participant-facing guidance must establish the intended meaning without
Tiizi inventing unsupported nutritional definitions.

### 28.4 Avoid Sugary Drinks

Participant-facing guidance must establish the intended meaning
sufficiently for consistent use.

### 28.5 Avoid Late-Night Snacking

Guidance must make clear that the actual late-night time window is
configured by the Challenge rather than universally fixed by canonical
Activity Knowledge.

### 28.6 Fasting

Appropriate safety and caution guidance is required before Runtime
publication.

These are content/publication dependencies. They do not invalidate the
canonical identities.

Other Activities may also require proportionate guidance before
production publication even where no specific dependency is recorded
here.

## 29. Admin evolution principle

The 118 Activities constitute the **Initial V2 Canonical Activity
Baseline**, not the complete or permanently closed Tiizi catalogue.

The Activity library is expected to evolve through governed Tiizi
administration.

Subject to the Knowledge Authority and delegation model, administrative
capability should eventually support appropriate operations such as:

-   add;
-   review;
-   refine;
-   relate;
-   publish;
-   unpublish;
-   retire;
-   replace where necessary.

The same general evolution principle applies to Challenge Templates.

Routine catalogue evolution that remains within the approved Knowledge
Governance model should not require reopening Stage EK merely because an
Activity is added, refined or retired.

A governance change is required where the governing model itself
materially changes.

## 31. Working substantive conclusions

The following working conclusions are established for continued Stage EK
development:

1.  Tiizi uses one unified Activity Knowledge architecture.
2.  Fitness and Wellness are domains within that architecture.
3.  Exercise Assets and Wellness Activity Assets remain domain-specific
    types beneath the common Activity foundation.
4.  The initial V2 canonical Activity baseline contains 118 candidates:
    84 Fitness and 34 Wellness.
5.  The baseline is fresh V2 knowledge design, not a preservation target
    for the historical catalogue.
6.  Activity identity remains separate from Challenge target and final
    Challenge configuration.
7.  Activity Knowledge establishes meaning, compatible measurement,
    guidance and governed relationships.
8.  Challenge Templates provide reusable starting configurations but are
    not final Challenges.
9.  Final Challenges determine the actual configured undertaking.
10. Sets, frequency, schedules, target values, Challenge type, scoring
    and similar concepts are not hardcoded into canonical Activity
    identity.
11. Metric compatibility does not require every theoretically possible
    Metric to be provisioned.
12. The six-Metric Founder Working Baseline remains sufficient across
    the initial 118 Activities.
13. Context does not automatically create duplicate canonical
    Activities.
14. Equipment, assistance, resistance, stance, grip, difficulty and
    similar changes normally remain Variants unless they materially
    change canonical meaning.
15. Activity Guidance should be useful and proportionate without
    creating unnecessary rigidity.
16. Canonical inclusion and Runtime publication readiness are distinct.
17. The Activity library is designed for governed evolution through
    Tiizi administration.
18. The initial baseline does not close the library against future
    addition, refinement, relationship changes or retirement.
