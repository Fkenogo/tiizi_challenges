# Wellness Activity Framework

**Version:** 1.0 (Phase 18C)
**Date:** 2026-06-28
**Status:** Approved for implementation in Phase 18D

---

## Core Rule

> **Activity identity is separate from target.**
> A wellness activity defines *what the user does*. The target defines *how much*.
> Activity names must never embed quantities.

| Bad | Good |
|---|---|
| `10-Min Mindfulness` | `Mindfulness` |
| `Daily Hydration 2L` | `Water Intake` |
| `8-Hour Sleep Streak` | `Sleep` |
| `5-a-Day Vegetables` | `Vegetable Intake` |

The `defaultTargetValue` and `defaultMetricUnit` fields pre-fill the challenge activity row. The user (or admin) can override them per challenge. The activity name stays stable regardless of target.

---

## Data Model

### `WellnessActivity` (current — no schema changes required for Phase 18D)

```ts
interface WellnessActivity {
  id: string;                     // stable slug — never changed once seeded
  category: WellnessCategory;     // routing key for icons, pickers, filtering
  name: string;                   // DISPLAY NAME — target-free (Phase 18D rename)
  shortName: string;              // SHORT LABEL — target-free (drives ID — do not change)
  description: string;
  difficulty: WellnessDifficulty;
  icon: string;
  activityType: WellnessActivityType;
  defaultMetricUnit: string;      // pre-fills unit in challenge form
  defaultTargetValue: number;     // pre-fills target in challenge form
  suggestedFrequency: number;
  benefits: string[];
  guidelines: string[];
  warnings?: string[];
  // ... protocol fields, bonus conditions, tags, timestamps
}
```

### `targetType` — planned addition

`targetType: 'daily' | 'cumulative' | 'weekly' | 'monthly'` is referenced in the framework spec as a signal for how the target should be interpreted by the scoring engine and displayed in challenge detail. It does **not** exist in the current interface.

**Phase 18D-1 scope:** add `targetType?: 'daily' | 'cumulative' | 'weekly' | 'monthly'` as an optional field to `WellnessActivity` in `src/types/wellnessActivity.ts`. It is optional so existing documents without it remain valid.

### ID stability rule

IDs are generated by `category-slugify(shortName)` in the catalog pipeline. IDs assigned by the admin UI use `slugify(name)`.

**Rule:** Never rename `shortName` for an existing activity. To rename the display label, change only `name`. IDs stay frozen once an activity is seeded into Firestore, because `challengeMembers`, `wellnessLogs`, and `wellnessTemplates` reference them by ID.

## ID Stability Strategy

### Rule 1: `shortName` is frozen for all 60 existing activities

The ID formula `category-slugify(shortName)` means shortName changes break all Firestore document lookups. Never change `shortName` for an existing activity.

### Rule 2: Name-only renames are safe and free

Changing `name` (the display label) requires only a catalog code edit + seed script run. No Firestore migration. Existing `challengeMembers` and `wellnessTemplates` reference `activityId` — not the name string.

### Rule 3: Retired activities are soft-retired, not hard-deleted

Retired activities are removed from the catalog array (so they no longer appear in pickers) but their Firestore documents are **not deleted**. Any existing challenge or template that references a retired activity ID continues to work because `wellnessActivityService.getActivityById` falls back to the local catalog when Firestore misses. Once an activity is retired from the catalog, the fallback also loses it — so Firestore documents for retired activities must stay in place.

**Recommended approach:** Remove retired activities from `WELLNESS_ACTIVITIES_CATALOG` (they disappear from pickers) but do not delete their Firestore documents. Any existing challenge/template referencing them still renders the stored `exerciseName` field from the challenge document itself, so users see the correct name.

### Rule 4: New activities get new IDs

New activities get `category-slugify(shortName)` IDs. These don't conflict with existing IDs because they use either a new category prefix (`movement-*`, `health-monitoring-*`) or new shortNames within existing categories.

### Rule 5: Category type additions require a TypeScript change before seeding

Adding `movement` and `health-monitoring` to `WellnessCategory` in `src/types/wellnessActivity.ts` must be done in Phase 18D-1 before the seed script runs in Phase 18D-4.

## Challenge Type Compatibility

All proposed wellness activities support all three challenge types:

| Challenge type | How it works | Example |
|---|---|---|
| **Competitive** | User with highest cumulative value wins | First to 100,000 steps; most meditation minutes |
| **Collective** | Group pools toward `groupCumulativeTarget` | Group walks 500 km; group logs 1,000,000 steps |
| **Streak** | Log daily target for `requiredConsecutiveDays` consecutive days | 30 days of water intake; 14 days of sleep logging |

`targetType` hints how the activity's contribution is summed for collective scoring:
- `daily` activities contribute `loggedValue` once per day
- `cumulative` activities may allow multiple logs per day (e.g. steps recorded by different apps)
- `weekly` / `monthly` activities are logged less frequently; streak behaviour should use `requiredConsecutiveDays` against calendar days, not log count
